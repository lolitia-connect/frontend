## 4. 功能级定制清单

### F01. 三端 Next App Router、初始化与 SSR 边界

入口：[user/app](../../apps/user/app/)、[admin/app](../../apps/admin/app/)、[payment-portal/app](../../apps/payment-portal/app/)。

- 三端从 Vite 启动/构建切到 Next.js 16；依赖声明 `next ^16.0.10`、React 19.2、应用 Tailwind/PostCSS 4.2.2。端口仍为 user 3000、admin 3001、payment 3002。
- 删除旧 main/index.html、TanStack 文件路由生成树、Vite config/插件和 SPA `_redirects`，建立 app/layout/page/template/providers。旧路由分组不进入 URL；OAuth/bind 使用 `[platform]`。
- [router-compat.tsx](../../packages/ui/src/lib/router-compat.tsx)用 Next Link/navigation 实现旧 `to/search/params/useNavigate/useSearch` 调用形状；保留 `$param` 插值和 query 序列化。它是生产适配层，不是死代码。TanStack Query/Table/Form 继续使用，不能按“TanStack”包名全部清除；共享 manifest 也仍保留 router 依赖。
- [user AppInitializer](../../apps/user/app/app-initializer.tsx)在挂载后读取配置/用户、注册 `window.logout`，保留运营配置 `custom_html`；[admin Bootstrap](../../apps/admin/app/bootstrap.tsx)挂载后请求配置/用户并安装会话失效处理，不在 prerender 阶段调用后端。
- admin 的 page 直接组合 section；读取 query 的日志/订单/用户等页面保留 Suspense 边界，日志筛选延续兼容层。日期格式化的 localStorage 读取增加 SSR guard。
- [payment page](../../apps/payment-portal/app/page.tsx)服务端读取 Authorization cookie，把 `initialAuthenticated` 传给 [PortalClient](../../apps/payment-portal/app/portal-client.tsx)；动态 import 不再 `ssr:false`，首屏登录/充值选择与客户端一致。cookie 存在只是初始界面选择，不代替后端鉴权。
- **SSR 不等于后端数据搬到 SSR 取。** 页面结构可 SSR，而 API bootstrap、storage、主题/语言恢复及 WebGL 仍在浏览器执行。不要重新给整页套 `ssr:false` 规避错误。
- 当前 app 中明确保留 client-only 的是 user/admin 导航进度条（依赖 search params）；WebGL 用 effect 内动态 import。既不能宣称“完全无 CSR”，也不能把“use client”误当成“不参与 SSR”。

### F02. API 环境变量、直连与独立部署

代码：[共享 request](../../packages/ui/src/lib/request.ts)、[user next.config](../../apps/user/next.config.ts)、[admin next.config](../../apps/admin/next.config.ts)、[payment next.config](../../apps/payment-portal/next.config.ts)。

- `import.meta.env.VITE_*` 改为 `process.env.NEXT_PUBLIC_*`；axios `baseURL` 实际读 **`NEXT_PUBLIC_API_BASE_URL`**，服务 URL 前缀读 `NEXT_PUBLIC_API_PREFIX`。不是 `NEXT_PUBLIC_BASE_URL`。
- user/admin 已无 Next rewrites，浏览器直接访问后端，后端必须允许站点 CORS；prefix 不再被代理剥离。没配 base URL 时不能假设存在 127.0.0.1:8080 SSR 兜底。
- **payment portal 是例外**：当前 [next.config.ts](../../apps/payment-portal/next.config.ts)仍保留 `/api/:path*` rewrite，目标 `${NEXT_PUBLIC_API_BASE_URL || "https://api.ppanel.dev"}/api/:path*`。共享 axios 的绝对 baseURL 请求和这条同源 rewrite 应分别理解，不能写成“三端均已删除所有代理”。
- 三份 [user](../../apps/user/netlify.toml)、[admin](../../apps/admin/netlify.toml)、[payment](../../apps/payment-portal/netlify.toml)部署配置使用根脚本 `build:user` / `build:admin` / `build:payment-portal`，发布各自 `apps/<app>/.next`，Node 26 与 Next 插件；不再用旧 dist/index.html SPA fallback。
- [根 netlify.toml](../../netlify.toml)仍属于 docs/VitePress（Node 20，docs 输出），不能拿它发布三端。app 配置中的路径按仓库根执行约定编写；Netlify UI 的 base/package/config 路径要匹配，不能机械把根相对路径再次拼进 app base。
- 公共 env 是构建期公开值，不能放真实密钥；示例中的默认登录信息只用于开发。保留 `NEXT_DIST_DIR` 隔离测试构建目录。
- 独立 Cloudflare Pages [functions](../../functions/)代理仍存在并由共享测试覆盖；删除的是旧 Vite dev proxy，不能混同为所有代理模块删除。

### F07. OAuth/绑定回调与 Telegram 邀请注册

代码：[OAuthMethods](../../apps/user/src/sections/auth/oauth-methods.tsx)、[认证 callback](../../apps/user/src/sections/oauth/certification.tsx)、[绑定 callback](../../apps/user/src/sections/bind/certification.tsx)、[Telegram helper](../../apps/user/src/utils/oauth/telegram-popup.ts)、[邀请码解析](../../apps/user/src/sections/auth/invite.ts)。

**路由与 popup：**

- OAuth/bind 的 Apple/Facebook/GitHub/Google/Telegram 共 10 个静态 index.html 桥接页全部删除；真实 App Router `/oauth/[platform]`、`/bind/[platform]`负责接收，不再跳回同一静态页形成循环。
- 发给提供方注册匹配的 redirect URI 保留末尾 `/`。页面内完成导航用 pathname，而非旧 `#/oauth/telegram`。
- Telegram 在点击事件中同步打开 about:blank popup，再等待后端授权 URL；避免 await 后才 window.open 被拦截。popup 不可用时退回整页授权。
- 兼容原生 `auth_result` 消息、桥接转发、query/hash 中 `tgAuthResult`、标准/URL-safe Base64、嵌套 payload。接收端按 popup source 或预期站点/提供方 origin 检查消息；不要夸大为所有分支都同时检查 source+origin。最终身份签名仍由后端验证。
- popup callback 先 relay 给 opener 并停止本窗口 token/bind 请求；主窗口进入真实 callback 路由后完成请求，防止用户“授权成功但主窗口没登录”。关闭时短暂等待消息，再请求提供方 `/auth/get` fallback；退出需清理 listener/timer 和 loading。

**两阶段邀请契约：**

1. 换 token 响应有真实 `token` 才设置 Authorization、刷新用户并跳转。
2. `invite_required:true` + `oauth_token` 表示身份已验证、尚未创建账号；callback 展示邀请码输入，ticket 仅保存在待注册状态，不当作登录凭据。
3. 第二步通过 [common service](../../packages/ui/src/services/common/common.ts) POST `/v1/auth/oauth/register`，载荷 `{oauth_token, invite}`；成功拿 token 才完成登录。错误邀请码可修改重试，可取消返回 auth。
4. 后端需要配套 `dc46571f` 或等价实现；ticket 10 分钟，由服务端缓存身份并在有效邀请之后创建用户。
5. 前端仍可携带 `cf_token/captcha_id/captcha_code/slider_token`，但当前后端 OAuth 请求结构只新增了 invite，不能将其描述为完整的后端验证码校验。见[后端 B04](../../../backend/.ai/sync-diffs/v1.21.7-local-2026-11-19.md#b04-强制邀请的-oauth-两阶段注册)。

现有针对性测试覆盖 popup 解析/转发、callback 和邀请 UI，真实浏览器提供方授权、弹窗策略与过期/并发仍需专门联调。此处不把源码测试的存在写成这次执行通过。
